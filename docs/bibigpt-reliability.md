## 已确认的问题

1. **本地排队被误当作服务器接收。** 工作台先写本地任务队列，立即返回本地 ID 并提示入队，随后才异步执行网络请求。旧代码等输入框清空/提示后马上关闭页面，未确认服务器接收。重新打开工作台又会恢复本地任务，和我们自己的同步总结轮询同时运行。
2. **轮询的并非任务状态。** `summaryBySetting` 即使 `isRefresh=false`，缓存未命中也可能执行新生成。旧代码每45秒调用它，实际日志中出现524及多次网络错误；不能据此判断后台字幕任务的状态。
3. **最后错误被初始风控覆盖。** 9月5日22:29提交的《土地收入，下降三分之二了》（BV1jCty6fEcE，9分22秒）后续六次查询均报“网络波动”，22:39等待耗尽后却把初始“平台风控”作为终态发给用户。现有日志没有其网页最终完成状态，因此不能声称网页任务失败。
4. **实际请求缺少超时。** 原先120秒配置只约束启动和导航，不约束 `page.evaluate` 内的 fetch；挂起会占住共用 profile，600秒等待预算也无法中断它。
5. **恢复路径不完整。** HTTP成功内嵌tRPC错误被误记成状态200；只有第一次出现风控才进队列，普通恢复中后来出现风控会被当作普通未就绪吞掉。
6. **网页还有内容准备后备入口。** 20:31真实联调中，`BV1XBbH6oE4V` 的 `contentPipeline.fetch` 返回500“平台风控”，但20:34对同一视频调用网页后备 `content.info` 成功拿到内容ID，状态为running。最初的管线改动遗漏了这条路径；已按当前前端补齐。不能仅凭已有字幕的两条成功样本判断新内容也稳定。
7. **并发操作提前删除工作提示。** 20:04 B站总结与评论分析对同一消息取得相同Typing reaction ID；评论先结束就删除仍在总结的提示，重复点击总结又重复删除。修复按消息及表情类型共享reaction计数，同类操作全部完成才删除；按用户要求，总结使用Typing、评论分析使用THINKING，分别显示和清理。同消息总结在完整回复结束前去重。

## 网页实际协议与改动

| 阶段 | 网页协议 | 客户端采用方式 |
| --- | --- | --- |
| 内容准备 | `contentPipeline.fetch`，失败后备 `content.info` | 正常forceFresh=false；后备映射相同audioConfig、isRefresh、skipSubtitleTask；等服务器返回dbId |
| 等待字幕 | `contentPipeline.observe`，按contentId查询 | 只看subtitle.status及错误元数据；不重新提交总结 |
| 总结 | 按准备入口选择 `contentPipeline.summarize` 或 `video.summaryBySetting` | ready后传原promptConfig/模型；content.info准备的内容走后者，不递归重建任务 |
| 章节 | `video.chapterSummary` | 保持现有中文timeline及展示边界 |

前端还会为界面读取字幕正文，但总结请求只需要URL和promptConfig。本项目据此省略字幕正文读取，不自行提取或总结字幕；当晚真实账号联调已验证可取得总结及章节。与网页最终跳转及章节请求一致，章节及分享链接使用内容准备返回的ID，不依赖总结响应是否另带id。

当前前端处理器的 `W()` 对fetch异常调用 `q()` → `content.info`，仅pipeline成功会给detail添加 `__pipelineWire` 标记；`G()` 按此标记选择总结入口。两路准备都失败时，普通风控不会由网页自动无限重试。本项目只做一次内容入口后备，并对认证、额度、限流、明确参数错误直接失败；这是比网页catch-all更保守的边界。

B站在browser模式、队列开关启用时直接采用这条流程，避免先触发一次同步风控。其他平台继续兼容原流程。字幕准备完成后，总结调用若遇超时或暂态5xx，最多三次允许缓存的补取，不重建字幕任务、不重复强制生成。等待状态、上游明确失败、认证失败和本地等待超时分别报告，日志保留阶段、contentId和最后错误；超时不宣称后台任务已失败。源平台提取所需授权与BibiGPT会话401/403分开提示。仍存在上游服务故障、登录失效和协议变化的可能，不能保证所有视频成功。
